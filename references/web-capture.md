# 路径 C：网页操作采集（本地版 Scribe）

脚本：`scripts/web_capture.py`。原理不是"识别截图里的字"，而是**浏览器里直接读 DOM**——这是它质量高于录屏的根本原因。

## 与录屏的质量差异

| 能力 | 录屏（路径 A） | DOM 采集（路径 C） |
|---|---|---|
| 截图清晰度 | 受视频编码压缩，文字有振铃伪影 | 原生 PNG，像素级锐利 |
| 高亮定位 | 靠模型目测估坐标，易偏移 | `getBoundingClientRect()`，零误差 |
| 打码 | 覆盖像素，可能漏边 | 按元素框精确定位，覆盖全 |
| 步骤判定 | 靠画面变化推测 | 每次 click/input 就是一步 |
| 文案素材 | 模型看图猜 | 元素文本/placeholder 直接给 |

## 敏感识别规则

`__sensitiveKind()` 按以下顺序判定，命中即标记为待打码：

| 条件 | 类型 |
|---|---|
| `type="password"` | 密码 |
| `maxLength === 1`，或 `inputMode="numeric"` 且 `maxLength ≤ 8` | 验证码 |
| 值为 11 位、`1[3-9]` 开头 | 手机号 |
| 值匹配邮箱格式 | 邮箱 |
| 值为 18 位（末位可为 X） | 身份证 |
| 值为 16~19 位数字 | 银行卡 |

**不在规则内的不会自动打码**：真实姓名、地址、头像、订单号、页面上的纯文本手机号（如"已发送至 138\*\*\*\*8000"）。这些必须人工复核补标注。

## 可见性判定（重要）

打码前用 `document.elementFromPoint()` 判断元素中心点最上层是不是它自己。若被弹窗/遮罩盖住，说明**用户此刻根本看不到**，跳过打码。

不做这个判断的后果：背景页被遮住的表单会被打码，马赛克块糊在弹窗上形成白斑（实测踩过）。

## 已知问题

1. **验证码多格逐字输入**会产生多条记录（每格一条）。精判时按 box 位置合并成一步。
2. **500ms 输入防抖**：打完一个字立刻点提交，可能漏记录该次输入。真实操作中极少发生。
3. **跨域跳转**后 `window.__steps` 会重置（新文档重新注入），跳转前的记录已截图留存，不影响。
4. **iframe 内的操作不采集**（init script 只注入主文档）。
5. **关闭浏览器才结束采集**，中途不要关标签页（脚本取 `ctx.pages[-1]`）。

## 扩展方案特有的坑（实测，均已修）

1. **`content_scripts` 只匹配 http/https**，`file://` 页面不会注入。测试时必须起本地 HTTP 服务，否则会误判成"扩展没加载"。
2. **content script 运行在隔离世界**，页面上下文里的 `window.xxx` 看不到它。不能用 `page.evaluate("window.__xxx")` 验证注入是否成功，要看实际有没有采集到步骤。
3. **坐标必须在事件瞬间取**。若延迟 100ms 再取，页面一切换，被点元素会被 `display:none`，`getBoundingClientRect()` 归零，整步被丢——实测因此丢失全部 3 次点击。
4. **`captureVisibleTab` 硬限速 2 次/秒**，无法绕过。超限时保留动作记录并标记 `no_shot`，**不要整步丢弃**：点击是教程最关键的一步，宁可无图也不能无记录。
5. **service worker 会休眠**，状态必须落在 `chrome.storage.local`，不能放内存变量。

## 与 render.py 的衔接

`web_capture.py` 产出的 `steps.json` 与路径 A 格式完全一致，直接：
```bash
python scripts/render.py <outdir>/steps.json <成品目录>
```
需要人工补的只有每步的 `title` 与 `body` 文案。
